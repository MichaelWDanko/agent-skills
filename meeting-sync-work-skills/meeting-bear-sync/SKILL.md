# Meeting Bear sync

Use this when running Job 2 of the meeting-notes pipeline: creating or recreating Bear notes from meetings that are already marked `ready` in local state.

## When to use
- A local meeting state store already exists
- Meetings have already been gated so only `ready` meetings can reach Bear
- Bear is the canonical editable surface for meeting notes after creation
- Later task extraction will depend on stable Next Steps formatting

## Core rules
- Do not create a Bear note unless the meeting state is `ready`
- Treat Bear as editable after creation: users may add tasks, change owners, or rewrite next steps later
- Do not invent owners for next steps
- If ownership is unclear, write `Owner unclear:` instead of `Team:`
- Preserve unknown-owner next steps for later validation instead of dropping them

## Note formatting rules
- Title format: `Mon DD, YYYY | Meeting Title`
- Do not repeat the meeting title as an H1 in the note body; Bear already displays the title separately
- Always tag with `work/meetings`
- Bear strips hyphens inside tag segments, so use sanitized tags such as `work/meetings` and `work/meetings/granola` rather than hyphenated variants
- Add `work/meetings/granola` when the note is based on Granola or mixed Google+Granola content
- If attendees are known, write them as a single bold inline line in comma-separated form: `**Attendees:** Name 1, Name 2, Name 3`
- If attendees are unknown, default to `**Attendees:** Michael Danko`
- Add a horizontal rule immediately after the attendees line, with no blank line above or below it
- The canonical Bear note should render as title, tags, attendees, `---`, then `## Meeting Details` with no extra spacer lines around the rule
- Use meeting-specific section headers
- Merge all usable sources into one consistent note body
- Do not create app-specific source sections such as `## Gemini Notes`, `## Granola Notes`, or repeated source-specific summaries
- Include exactly one `## Next Steps & Takeaways` section in the final note
- Bold the named person in each takeaway/action bullet when a person is named, e.g. `- [KRYPTON-20260330-1] **Michael Danko**: Confirm Vienna on deployment timing.` Keep the task key itself unbolded.

## Stable task key pattern
Use meeting-scoped visible keys in `## Next Steps & Takeaways`.

Examples:
- `[INTERCOM-20260327-1] Michael Danko: follow up with Jean`
- `[KRYPTON-20260330-1] Owner unclear: review and deploy approved code changes`
- `[BOSTON-MONTHLY-20260408-01] **Michael Danko**: confirm next-step ownership for the Boston sync.`

Guidance:
- Derive the visible key from 1 or 2 primary words from the meeting title plus the meeting date, not from a global counter
- Prefer a short slug like `BOSTON-MONTHLY`, `KRYPTON-STANDUP`, or `JUSTIN-PR` instead of repeating the full title
- Do not generate keys from the whole meeting title. For example, use `[JUSTIN-PR-20260420-01]`, not `[QUICK-CONNECT-WITH-JUSTIN-PR-20260420-01]`
- Format the key as `SLUG-YYYYMMDD-##` so it stays unique and readable
- Keep keys stable across edits and updates
- If newly generated keys accidentally use a full-title slug, repair the visible keys in the Bear note and update the generation prompt before continuing the backlog
- Preserve existing user-edited keys if updating a note later
- New manual unkeyed tasks added in Bear can be assigned keys on a later reconciliation pass
- Internally, combine `event_id + task_key` for uniqueness rather than relying on the visible key alone
- Bold the named person in each takeaway/action bullet when a person is named; keep the key itself unbolded

## Source synthesis guidance
- Granola-only meetings: fetch Granola meeting details and summarize into the standardized Bear format
- Mixed-source meetings: combine usable Google Doc/Gemini content with Granola details
- Google Doc-only meetings: use usable document content fetched through Google APIs
- Treat local state previews as hints only, not as sufficient source material for final Bear note creation
- Before drafting a Bear note, fetch full content for every usable source whenever possible
- If a source is not usable, do not pretend it contributed content
- If full source retrieval fails for a meeting that would otherwise sync, fail closed: skip Bear creation or update and report the meeting for manual review rather than writing an incomplete canonical note
- If the only available source is a stub, empty transcript, or non-substantive autogenerated placeholder with no real discussion content, do not create a canonical Bear note; mark the meeting missing for Bear sync instead of writing a fake minimal note

## Pre-write validation checklist
Before creating or updating a Bear note, verify all of the following:
- the Summary is complete prose, not a clipped fragment or flattened heading dump
- there are no duplicate section headers
- there are no app-specific source sections such as Gemini Notes or Granola Notes
- there is exactly one `## Next Steps & Takeaways` section
- the final note reflects the main decisions, discussion points, and action items from all usable fetched sources

If these checks fail, do not write the note until the source retrieval or synthesis issue is fixed.

### Practical Granola fallback
If direct Granola MCP access is unavailable but the state contains a Granola share URL, the public notes page can still be usable.

Observed fallback:
- open the shared `https://notes.granola.ai/d/<id>` page directly
- the page often renders enough structured content to recover headings, bullets, and summary text without login
- useful data may also appear inside the page HTML as escaped content and Open Graph metadata

Implication:
- Job 2 can still create Bear notes from Granola-backed meetings even when Granola MCP is not callable in the current runtime
- prefer the actual rendered/shared content over inventing summaries from thin local metadata

## Practical Google Doc retrieval fallback
When a meeting is Google-Doc-backed and local state only contains `content_preview`, do not draft from the preview alone.

Observed failure modes:
- browser automation may be unavailable if the local Playwright browser bundle is missing
- anonymous `curl` export URLs can return a Google sign-in or cookie wall instead of the document text

Reliable fallback on this machine:
- use `/Users/michaeldanko/.hermes/venvs/google-workspace/bin/python`
- load OAuth credentials from `/Users/michaeldanko/.hermes/google_token.json`
- call the Google Docs API directly with `google.oauth2.credentials`, `google_auth_httplib2.AuthorizedHttp`, and `googleapiclient.discovery.build`
- fetch the full document with `docs.documents().get(documentId=<doc_id>)`
- extract paragraph text from `body.content[].paragraph.elements[].textRun.content`

Implication:
- Job 2 can recover full Google Doc note content even when browser and export-based retrieval both fail
- prefer this authenticated Docs API fallback over writing a Bear note from truncated `content_preview`

## Local state expectations
Meeting state should retain Bear metadata separately from source detection.
Useful fields:
- `bear_status`
- `bear_note`
- `bear_synced_at`
- `source_last_modified_at`

Treat `bear_synced_at` as the last successful Bear write time. If any source's `last_modified_at` or equivalent freshness marker is newer than `bear_synced_at`, the meeting should be considered stale and eligible for Bear update rather than only Bear creation.

Recommended helper commands in the local project:
- `list-bear-candidates`
- `mark-bear-created`
- `mark-bear-updated`
- `mark-bear-missing`

## Bear identifiers
- Prefer storing the real Bear note UUID in local state, not a weak placeholder such as `created-via-api`
- If note creation returns only a weak identifier, immediately look up the created note by exact title in Bear and store the real UUID when available
- If Bear read/search is blocked by permissions and the exact-title lookup cannot recover a UUID, keep `created-via-api` in local state and continue the sync instead of stalling the pipeline
- This makes later deletion recovery and reconciliation much safer

## Encoding pitfall discovered in practice
- Do not URL-encode the note title or markdown body before sending it to Bear
- A note titled like `Mar+30,+2026+|+Krypton+Stand+Up` indicates the payload was encoded too early, usually via `quote_plus`/`urlencode` or a query-string path
- If Bear creates a note whose visible title or body contains `+` in place of spaces, treat it as a bad duplicate and recreate it using raw plain-text content
- Validate that the draft title still contains spaces and `|` before writing or calling Bear MCP
- Keep URL encoding only for transport-layer fields that explicitly require it, not for the note text itself

## Practical sync finding from Job 2
- On some macOS setups, Bear writes may succeed while exact-title search/lookup remains permission-limited
- In that case, Hermes-driven Bear operations may report success but still return only a weak identifier or a null lookup result
- Treat that as a Bear permissions problem, not as a failed sync, and record the strongest identifier available in state
- Avoid repeated lookup retries once the exact-title lookup has already failed for permission reasons
- When direct MCP scripting is awkward, `hermes chat -Q --source tool` can be used as the operational caller for Bear MCP tools during Job 2; load the Bear integration skill and ask for strict JSON so the returned note identifier can be captured and written into local state
- After create/update returns `created-via-api`, immediately do an exact-title lookup and replace the weak identifier with the recovered Bear UUID or numeric note id when available

## Important recovery pattern
If a Bear note was manually deleted but local state still says it was created:
1. Reset local state first with a helper like `~/.hermes/venvs/google-workspace/bin/python ~/Projects/agent-meeting-notes-sync/scripts/state_tools.py mark-bear-missing --event-id <event_id> --reason deleted_in_bear`
2. Only reset the specific meeting record, not the whole state file
3. Recreate the note in Bear
4. Mark it created again in local state using the real Bear UUID when available

Important execution note:
- On this machine, running `python3 scripts/state_tools.py ...` may fail because the system Python can’t parse the file’s modern type-hint syntax
- Use `~/.hermes/venvs/google-workspace/bin/python` for state_tools commands instead of bare `python3`

Why this matters:
- Otherwise Job 2 may skip the meeting because local state incorrectly says the note still exists

### When the user only has Bear UUIDs
Sometimes the user knows the deleted Bear note UUIDs but not the calendar event ids.
In that case:
- search `state/meeting_sources.json` for `bear_note.identifier` values matching those UUIDs
- map each UUID to its meeting record and calendar `event_id`
- clear only `bear_status`, `bear_note`, and `bear_synced_at` for the matched records
- leave Google and Granola detection fields intact so the meetings stay eligible for future Bear recreation

Observed real-world outcome:
- a batch of Bear UUIDs can be safely cleared from local state without touching Bear itself
- after cleanup, those meetings will appear as `ready` + `not_created` candidates for the next Bear sync run

## Practical Bear MCP finding
Bear note creation may work even when Bear read/search remains impaired by macOS Full Disk Access restrictions.

Implication:
- You may be able to create notes successfully
- But duplicate detection, search, or note lookup may still fail or return weak identifiers like `created-via-api`
- Always try an exact-title lookup immediately after create/update so you can recover the real Bear note ID before writing local state
- In practice, `mcp_bear_get_note_by_title` can return a stable numeric ID even when create returns `created-via-api`, and that numeric ID is the best value to store in state
- If exact-title lookup succeeds, prefer the numeric ID over the weak create response for later reconciliation and duplicate checks

Additional runtime finding:
- direct MCP tool calls may hang even when the underlying Bear service can still create notes
- as a fallback on macOS, calling the installed Bear service module directly through Node and `BearService.createNote()` can still succeed because it writes through Bear x-callback URL rather than protected database reads
- this fallback still returns the weak identifier `created-via-api`, so local state should store that exact identifier only if the exact-title lookup cannot recover a stronger ID

Tag behavior observed in practice:
- Bear may auto-add a parent tag like `work` when creating notes under `work/meetings`
- do not treat that extra parent tag as a sync failure
- keep using sanitized tags such as `work/meetings` and `work/meetings/granola`

Recent run notes:
- On this machine, the Hermes CLI wrapper was not always on `PATH`; invoking it via `/Users/michaeldanko/.hermes/venvs/google-workspace/bin/python /Users/michaeldanko/Projects/hermes-agent/hermes_cli/main.py mcp ...` worked reliably
- `hermes mcp list` and `hermes mcp test bear` are useful for confirming that the Bear server is configured and discoverable before attempting note writes
- If `npx` is missing from `PATH`, try `/opt/homebrew/bin/npx` or temporarily prepend `/opt/homebrew/bin` to `PATH`
- The Bear database lives at the default macOS Group Containers path, and exact-title recovery can be checked with SQLite when Bear read permissions allow it
- After an x-callback create attempt, allow a short delay before doing exact-title recovery or state reconciliation, since the UI write may not be instantly reflected in local database queries

## Recommended workflow
1. List `ready` meetings with `bear_status=not_created`
2. Process a small deterministic oldest-first batch rather than the whole backlog at once
3. For each selected meeting, inspect usable local Google content and/or Granola match data
4. Fetch full source content before drafting; do not rely on state previews alone
5. Search Bear by exact expected title before creating anything to avoid duplicates
6. Draft the Bear note in the standardized format
7. Validate that the note is complete, non-truncated, has no app-specific sections, and contains exactly one `## Next Steps`
8. Write keyed next steps using explicit owners or `Owner unclear`
9. Create or intentionally update the note in Bear
10. If Bear returns a weak placeholder ID such as `created-via-api`, immediately look up the note by exact title and capture the real Bear UUID before writing state
11. Record the result in local state with the strongest available Bear identifier
12. If a user later deletes the note in Bear, reset local state before recreating it
13. When verifying an end-to-end Job 2 run, prefer executing the underlying local detector and Bear-sync commands directly rather than relying on a cron wrapper’s manual `run` action; confirm the result with `state_tools.py summary`, `list-bear-candidates`, and exact-title Bear lookups
14. The JSON returned by `list-bear-candidates` is the actual worklist for the current run. There is no helper command that processes all Bear candidates in one shot. Do not invent subcommands like `mark-bear-candidates`.
15. Job 2 should process every candidate returned for the run unless the operator explicitly sets a smaller batch limit in the command.
16. Job 2 does not rescan Calendar on its own; it only consumes whatever the detector wrote into the shared state file, so if the state file is empty or deleted, rerun Job 1 first
17. When multiple candidates are returned, isolate each meeting by using one delegated child session per meeting so Bear drafting cannot leak phrasing or assumptions between meetings
18. Pass only one candidate’s source payload to each child session, not the whole candidate batch
19. A good parent/child split is: child drafts one meeting note and returns title, tags, source kind, and note body; parent calls Bear MCP and runs the exact `mark-bear-created` / `mark-bear-updated` / `mark-bear-missing` helper command.
20. Keep delegation enabled in the meeting-sync profile only if the child tool surface is still narrow enough to preserve isolation and avoid accidental cross-meeting context reuse
21. For cron delivery, assume there is only one final job message. Summarize the run with one concise line per meeting actually processed plus a totals line; do not ask follow-up questions or emit internal commentary.
22. The parent session must maintain an explicit in-memory run ledger for every candidate returned by `list-bear-candidates`, with one entry per meeting marked `created`, `updated`, or `failed`.
23. Never emit a success summary like `created 0, updated 0, failed 0` when `list-bear-candidates` returned one or more candidates. If candidates were returned, every candidate must appear in the run ledger and the final totals must equal the ledger counts.
24. Before sending the final cron response, verify that the totals line matches the per-meeting result lines exactly. If the ledger is incomplete, report a failure instead of a success.
25. Never expose execution chatter in the final response. Do not mention tool names such as `terminal`, `process`, `read_file`, `browser`, or `execute_code`. Do not say `I will`, `I am going to`, `let me`, or narrate retries, planning, or self-corrections.
26. If an intermediate step fails, keep working silently when recovery is possible. Only the final cron response should be user-facing.
27. The final cron response must be one of only two forms: a concise per-meeting result summary plus totals, or one concise failure summary. No preamble, no explanation of tool selection, and no internal notes.
28. If you manually delete Bear notes for revalidation, reset only the matching meeting records in local state by clearing Bear status through `mark-bear-missing`; do not wipe the whole state file or re-run unrelated detection work.
29. For Job 2 cron runs, treat `list-bear-candidates --limit 1 --offset 0` as the only worklist source and loop until it returns `count: 0`; process meetings strictly one at a time and update local state immediately after each Bear write.
30. Determine `source_kind` exactly as `google_doc`, `granola`, or `mixed`, and always tag notes with `work/meetings` plus `work/meetings/granola` only when Granola materially contributed.
31. If Bear only returns the weak identifier `created-via-api`, keep it as the state identifier when no stronger UUID or note id is available rather than stalling the sync.
32. A Google-Doc-backed meeting with usable Gemini content still counts as `google_doc` source kind; do not invent a mixed source unless Granola materially contributed.

## Why this skill exists
A reliable Job 2 flow needs more than just note creation. It also needs:
- state reconciliation after manual Bear deletions
- task-friendly next-step formatting for later Job 3 extraction
- support for manual edits in Bear without losing task identity
